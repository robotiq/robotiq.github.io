# Step-by-step: adding a new software tool

The steps below add a Python tool for the **Adaptive grippers** family hosted
at `https://github.com/robotiq/2f85-python-driver`. Every product/tool page
(versioned or not) lives under `software-tools/` and is served by the
shared `software-tools` Docusaurus instance — see
[Documentation versioning](./versioning) for why: two plugin instances
can't split ownership of one URL prefix, and every tool's page lives under
`/docs/drivers/*`.

**If the new tool is Robotiq-maintained and submodule-synced** (as opposed
to a third-party or not-yet-available tool), it should usually also join
the sitewide **Stable / Development (main)** switcher, matching every
other Robotiq-maintained tool on this site — see
[Documentation versioning](./versioning) once the steps below are done.
That's just two extra steps (tagging the sync job with a `toolId`, and
one `versioned(...)` entry in the nav tree — see
[Documentation versioning](./versioning#checklist-adding-versioning-to-a-new-tool)'s
checklist) — it doesn't change where the tool's files live or how the
sync job itself is declared, both already the same either way; only
whether that tool participates in Stable/Development (main) cuts.

## 1. Add the submodule

This registers the tool's repository as a pinned import under
`external/`. Every contributor who clones this site will get the
same version of the source repo.

```bash
git submodule add \
  https://github.com/robotiq/2f85-python-driver \
  external/2f85_python
git submodule update --init
```

## 2. Declare the sync job

Open [`scripts/external-jobs.js`](https://github.com/robotiq/robotiq.github.io/blob/main/scripts/external-jobs.js)
and add an entry inside a `submoduleJobs(submodule, { repoUrl, branch },
[...])` call — that helper merges the shared `submodule`/`repoUrl`/`branch`
fields into every job passed to it, so a submodule with several jobs
(README, docs/, API reference, ...) states them once instead of repeating
them on each entry. Start a new call for a new submodule:

```js
...submoduleJobs('2f85_python', { repoUrl: 'https://github.com/robotiq/2f85-python-driver', branch: 'main' }, [
  { from: 'README.md', to: 'Adaptive grippers/Libraries/Python/_readme.md', destRoot: 'software-tools' },
]),
```

`destRoot: 'software-tools'` is what every driver job needs (see
[Documentation versioning](./versioning)) — content outside `software-tools/`
lands in the default `docs` instance's own tree instead, which doesn't
serve anything under `/docs/drivers/*`.

For a repo that contains multiple tools, add one job per tool inside the
same call:

```js
...submoduleJobs('2f85_drivers', { repoUrl: '...', branch: 'main' }, [
  // C++ tool
  { from: 'sdk_cpp/README.md', to: 'Adaptive grippers/Libraries/C++/_readme.md', destRoot: 'software-tools' },
  // Python tool
  { from: 'python/README.md', to: 'Adaptive grippers/Libraries/Python/_readme.md', destRoot: 'software-tools' },
]),
```

If the submodule already has a `submoduleJobs(...)` call elsewhere in
`JOBS` (e.g. you're adding a second tool from a repo already used for
another one), add your job to its existing `jobs` array instead of
starting a new call — one `submoduleJobs(...)` per submodule.

Test locally:

```bash
node scripts/sync-external-docs.js
```

## 3. Create the wrapper page

Create `software-tools/Adaptive grippers/Libraries/Python/index.mdx`. This file
is tracked in git and controls the page title, sidebar label, and
any introductory text above the synced README:

```mdx
---
title: Python
sidebar_label: Python
sidebar_position: 2
---

![Libraries](https://img.shields.io/badge/Category-Libraries-lightgrey)

![Supported by Robotiq](https://img.shields.io/badge/Supported_by-Robotiq-blue)

Brief description and link to the source repository.

## Intro

import Readme from './_readme.md';

<Readme />
```

The `## Intro` heading and the import are optional — omit them if
there is no synced README or if the content should start directly.

**Both badges are required, not decorative** — `generate-tools-table.js`
walks the folder tree looking for the `Category` badge to decide which
table a page belongs to, and reads the `Supported_by` badge for the cell
shown in that table (see
[Auto-generated software tools tables](./tools-tables)). Valid `Category`
values: `Libraries`, `Simulation`, `Other`, `ROS`. Use
`Supported_by-Robotiq-blue` for tools developed and maintained by Robotiq,
or `Supported_by-Third_party-lightgrey` for community-maintained tools.

**`ROS` is one page per product, not one per distro or generation.**
There's no `ROS1`/`ROS2` split — a product gets at most a single
`Category-ROS` leaf, `software-tools/<Product>/ROS/index.mdx`, covering
whatever ROS integration that product has. Which specific ROS distros it
supports is the driver's own repo README's job, not this page's. For a
Robotiq-maintained ROS driver, this page is synced exactly like the
Tactile Sensor C++ library page in [step 3 above](#3-create-the-wrapper-page) —
a submodule, a sync job pulling its README, and a thin wrapper importing
it:

```mdx
---
title: ROS
sidebar_label: ROS
---

![Category](https://img.shields.io/badge/Category-ROS-lightgrey)
![Supported by Robotiq](https://img.shields.io/badge/Supported_by-Robotiq-blue)

Brief description and link to the source repository.

## Intro

import Readme from './_readme.md';

<Readme />
```

For a third-party ROS integration, write it by hand instead, same as any
other no-README tool (see "No README or no software tool yet?" below) —
`Supported_by-Third_party-lightgrey`, short description, and a
**Reference:** link to the community repository.

Since this page is now a single leaf directly under `ROS/`, not a
container, it does **not** get a separate dedicated landing page the way
Libraries/Simulation/Other do — see
[step 4](#4-create-the-product-landing-page) for why.

**No README or no software tool yet?** Skip steps 1 and 2 entirely
and write the `index.mdx` manually. This is the right approach when
a tool is planned but not yet available, or when the source repo has
no suitable README to pull in. Write the page content directly with
no import:

```mdx
---
title: Python
sidebar_label: Python
sidebar_position: 2
---

![Libraries](https://img.shields.io/badge/Category-Libraries-lightgrey)

![Supported by Robotiq](https://img.shields.io/badge/Supported_by-Third_party-lightgrey)

Coming soon. In the meantime, see
[org/repo](https://github.com/robotiq/...) on GitHub.
```

The page still appears in the sidebar and can be updated to import
a synced README later, once the tool or its documentation exists.

## 4. Create the product landing page

If the product folder has no `index.mdx` yet, create
`software-tools/Adaptive grippers/index.mdx`:

```mdx
---
title: Adaptive grippers
sidebar_label: Adaptive grippers
sidebar_position: 0
---

Short description of the product family.

## Available drivers

{/* AUTO-GENERATED-PRODUCT-LIBRARIES-TABLE:START */}
{/* AUTO-GENERATED-PRODUCT-LIBRARIES-TABLE:END */}

{/* AUTO-GENERATED-PRODUCT-ROS-TABLE:START */}
{/* AUTO-GENERATED-PRODUCT-ROS-TABLE:END */}

{/* AUTO-GENERATED-PRODUCT-SIMULATION-TABLE:START */}
{/* AUTO-GENERATED-PRODUCT-SIMULATION-TABLE:END */}

{/* AUTO-GENERATED-PRODUCT-OTHER-TABLE:START */}
{/* AUTO-GENERATED-PRODUCT-OTHER-TABLE:END */}
```

Don't write any of these tables by hand — leave each marker pair where
shown and `scripts/generate-tools-table.js` fills in a single-row version
of the matching category's table (see
[Auto-generated software tools tables](./tools-tables)) on the next
build, including that category's own heading (e.g. `### Libraries`,
`### ROS`) written *inside* the marker pair. A category with no tool yet
writes nothing between its markers at all — heading included — so leave
each empty pair exactly as shown above; the whole section simply won't
appear until it has its first tool.

**For each of `Libraries`/`Simulation`/`Other` the product actually has
any tool pages in**, *also* create a matching dedicated sub-page, e.g.
`software-tools/Adaptive grippers/Libraries/index.mdx`:

```mdx
---
title: Libraries
sidebar_label: Libraries
---

{/* AUTO-GENERATED-PRODUCT-LIBRARIES-TABLE:START */}
{/* AUTO-GENERATED-PRODUCT-LIBRARIES-TABLE:END */}
```

This is what a click on that category in the sidebar actually lands on —
the product page's own table is a quick, at-a-glance summary, and the
dedicated page is where that summary is reachable as its own page.
`generate-tools-table.js` throws a build error naming the missing file if
a product has tool pages in one of these three categories but no matching
`<Category>/index.mdx` with these markers; a category with **no** tool
pages for this product never gets one at all — nothing to make a page
out of, so that category's whole section simply doesn't appear on the
product's own page, above, and there's no dedicated page either.

**`ROS` is the one exception — it never gets a dedicated landing page.**
A product has at most one `Category-ROS` leaf, so there's no multi-item
table to land on beyond the leaf page itself; `ROS/index.mdx` created in
[step 3](#3-create-the-wrapper-page) above is both the category folder
*and* the real content page, with no separate landing step here.

## 5. Register in `site-nav-tree.mjs`

Add the tool's node to `scripts/site-nav-tree.mjs`'s `SITE_TREE` — the
single source of truth for the whole "Software Tools" nav tree, shared by
`sidebars.software-tools.js` (the real sidebar) and `sidebars.js`'s
`overviewSidebar` (the plain-link copy shown on `docs/intro.mdx`, which
lives on a different plugin instance and can't display this one's sidebar
directly). Doc ids are relative to `software-tools/`, with no `drivers/`
prefix — that prefix is only the URL's own `routeBasePath`, added by
Docusaurus itself, not part of the doc id:

```js
category('Adaptive grippers', [
  category('Libraries', [
    leaf('Adaptive grippers/Libraries/C++/index'),
    leaf('Adaptive grippers/Libraries/Python/index'),
  ]),
  leaf('Adaptive grippers/ROS/index'),
  category('Simulation', [
    leaf('Adaptive grippers/Simulation/Isaac Sim/index'),
    leaf('Adaptive grippers/Simulation/PyBullet/index'),
  ]),
  category('Other', [
    leaf('Adaptive grippers/Other/GraspGen/index'),
  ]),
], 'Adaptive grippers/index'),
```

`ROS` is a plain `leaf`/`versioned` node, not a `category` — a product
has at most one `Category-ROS` page, so there's nothing to expand into.
`category(label, items, docId?)` takes an optional trailing doc id, only
when that category's own landing page exists (e.g. the product's own
`index.mdx`) — omit it and the category header is still expandable, just
not itself clickable, same as Force Torque Sensor's entry (no
`Simulation`/`Other` groups yet, since it has no tools there).

**A submodule-backed tool that also joins Stable/Development (main) versioning** uses
a `versioned(label, toolId)` node instead of `leaf(docId)` — see
[Documentation versioning](./versioning#checklist-adding-versioning-to-a-new-tool)
for the full checklist (it also needs its sync job in
`scripts/external-jobs.js` tagged with that same `toolId` — everything
else, `scripts/versioned-tools.js` and `sidebars.software-tools.js`'s
`activeItems` map, derives from that automatically).
