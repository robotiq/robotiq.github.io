# Documentation versioning

The whole site has one, sitewide **Stable / Development (main)** switcher
(the dropdown at the top of every page) — not a per-tool one. **Stable**
means every Robotiq-maintained, submodule-synced tool at its own newest
tag; **Development (main)** means every one of them at its own live `main`
branch. Each tool can still be at a different *tag* (tactile_sensors'
Stable might be `v2.0.0` while grippers' is `v1.0.0`), but there's exactly
one sitewide *choice* between "released" and "in progress," and it's the
same choice everywhere on the site, not something picked separately per
tool page. A tool that isn't submodule-synced (a hand-authored placeholder
like PyBullet/MuJoCo/GraspGen, or a product with no submodule at all like
Force Torque Sensor/EPick) has no Stable/Development split at all — it
stays on the plain, single-version pattern described in
[Adding a new software tool](./adding-a-tool). See the
[API stability policy](/docs/api-stability) for what this means for a
reader deciding which version to build against.

## One shared instance, not one per tool

Docusaurus versions a `docs` plugin instance as a whole, not individual
pages — there is no way to version some pages while others on the same
instance stay unversioned. Every submodule-synced tool's content lives in
**one** shared `@docusaurus/plugin-content-docs` instance,
`versioned-tools` (`docusaurus.config.js`'s `plugins` array), with
`path: 'versioned-tools'` and `routeBasePath: 'docs/drivers'` — every
tool's own subfolder under `versioned-tools/`, all versioned together. A
single tool used to get its own separate instance instead (one per
versioned tool); that meant a version dropdown per tool page, a
hand-written sidebar file per tool, and no way to remember a reader's
version choice across the whole site — the reason for the current shape.

**Content lives under a top-level `versioned-tools/<Product>/<Tool>/`
folder, never nested inside the main `docs/` tree** — even fully covered by
that instance's own `exclude`, nesting a second plugin instance's files
inside the default instance's `docs/` reproducibly breaks MDX compilation
with a bogus, content-independent `Unexpected FunctionDeclaration ...
non-esm` error (confirmed by bisection: moving the exact same files outside
`docs/` fixed it immediately, no content change). A `sync-external-docs.js`
job opts into this with a `destRoot: 'versioned-tools'` field (default is
`'docs'`, so every non-versioned job is unaffected) — see the jobs in
`scripts/external-jobs.js` for the real shape, and the big comment on
`destRoot`/`currentDocsRoot`/`currentRoutePrefix` near the top of
`sync-external-docs.js` for how a `doxygen2docusaurus` job's slug/backlink
generation adapts. `apiFolderPath` there is always the doc id relative to
the *owning instance's own root* — for a tool sharing the `versioned-tools`
instance with others, that means the tool's own full subpath (e.g.
`'Adaptive grippers/Libraries/C++/API'`), never shortened to a bare tail
like `'API'`: multiple tools' own doxygen jobs sharing one instance could
otherwise collide on the exact same generated doc ids and the same sidebar
cache file.

## Why not full per-tag archiving

This site aggregates N independently-released repos (currently 3
submodules) — there's no single "site version" a `grippers` release and a
`tactile_sensors` release both correspond to, so full per-tag versioning
(one archived build per release, per tool) would multiply without bound as
tools and tags are added. The chosen shape stays bounded at **exactly two
real states, forever**:

- **Stable** — every tool at its own newest tag. A real, released state,
  re-cut whenever any tool's tag moves. Owns the site's root URL
  (`path: ''`) — the default a bare link, a search result, or a
  first-time visitor lands on, since that's the state this site actually
  makes a compatibility commitment about.
- **Development (main)** — every tool at its own live `main`, unchanged in
  content from before this feature existed, just relocated off the root
  URL to `/next` (`path: 'next'`) and tagged `banner: 'unreleased'` +
  `noIndex: true` (kept out of search/sitemap). May include unreleased,
  uncommitted API changes at any time.

An older-than-Stable release isn't archived on this site at all — a reader
chasing a specific older tag goes to that tag on GitHub directly, the same
place `git tag`/GitHub Releases already is the source of truth. That's a
deliberate trade-off, the same one this design always made: it keeps this
site's own build count bounded regardless of how many releases a tool
accumulates, while still answering the common case (a reader on the
current release, or chasing `main`) directly.

## Which version the root URL serves

```js
versions: {
  current: { label: 'Development (main)', path: 'next', banner: 'unreleased', noIndex: true },
  stable: { label: 'Stable', path: '' },
},
```

`stable` takes the empty `path: ''` — Docusaurus serves whichever version
has that path at the instance's own root URL, with no version segment in
the URL at all. `current` moves to `path: 'next'` instead (matching
Docusaurus's own convention for unreleased docs elsewhere), and carries
`banner: 'unreleased'` (renders the `src/theme/DocVersionBanner/index.jsx`
warning — see [API Stability Policy](/docs/api-stability)) and
`noIndex: true` (a `<meta name="robots" content="noindex">` tag, so search
engines and the sitemap never send a reader to unreleased docs by
default). Neither label carries a tag — with one shared instance covering
several tools that can each be at a different tag, there's no single
sitewide version number to print in the dropdown; see
[Per-page tag banners](#per-page-tag-banners) below for where each tool's
own tag actually shows up.

**Bootstrapping the very first cut.** `lastVersion: 'stable'` (and the
`stable` entry in `versions` above) can only resolve once `stable` is a
version that already exists in `versioned-tools_versions.json` — every
`docusaurus`/`docs:version:` CLI invocation validates both against
whatever's actually in that file, *including* the very first
`docs:version:` call that's about to create `stable` for the first time
ever. `docusaurus.config.js` reads that file itself and falls back to
leaving `lastVersion` unset and the `stable` entry out entirely until it
sees `stable` already there — self-bootstrapping, no one-time manual
config edit needed for a brand new site.

## Per-page tag banners

`src/theme/DocVersionBanner/index.jsx` renders on every submodule-backed
tool's own page, on both versions — not just the `unreleased` warning on
Development (main) (stock Docusaurus's own behavior), but also an info
line on Stable, both naming that specific page's own tag (e.g. "Use Stable
(v1.0.0)", "This page reflects Stable v1.0.0"). It works out which
submodule a page belongs to from the page's own doc id (`findToolId`,
matched against each tool's `toolPath` in `scripts/versioned-tools.js`)
and looks its tag up in `versioned-tools-stable.json` directly (imported
into the client bundle, not looked up over the network) — the same file
`scripts/cut-version.js` writes to when it cuts Stable.

`useDocsVersion()`'s returned version metadata names the version field
`version`, not `name` — confirmed the hard way (an early version of this
code checked `.name`, which is `undefined` on that object, and silently
rendered no Stable banner anywhere, on every page, with no error). The
`GlobalVersion`-shaped object `useDocVersionSuggestions()` returns
(`latestVersionSuggestion` in `DocVersionBannerEnabled`) is a *different*
type that does use `.name` — easy to mix up since both objects describe
"a version" and sit right next to each other in the same file.

## The version dropdown is sitewide

`docusaurus.config.js`'s navbar has one `docsVersionDropdown` item,
`docsPluginId: 'versioned-tools'` — Docusaurus's stock behavior for this
navbar item type is to render on *every* page, site-wide, falling back to
a plain link to that instance's `lastVersion` outside the instance's own
pages rather than disappearing. That's exactly "the dropdown is always on
top of the site" (an explicit requirement) for free, with no custom
component needed — a single shared instance means there's only ever one
dropdown to show, unlike the old per-tool-instance shape, which needed a
custom `useActivePlugin`-gated wrapper (deleted) specifically to *hide*
each tool's own dropdown outside that tool's own pages, so N of them
wouldn't all show at once.

## Sticky version preference across visits

Docusaurus already remembers a visitor's last-chosen version in
`localStorage`, per plugin id (`useDocsPreferredVersion`, written whenever
the dropdown or a `DocVersionBanner` suggestion link is used), and already
keeps a visitor in that version while they click internal links. The one
thing it doesn't do on its own: honor that stored preference when landing
on a `versioned-tools` page whose *own* version doesn't match it — most
commonly the site root, which always serves Stable regardless of what a
returning visitor picked last time. `src/theme/Root/index.jsx` (a
swizzled `Root`, wrapping the whole app) closes that gap: on every route
change, if the current page belongs to `versioned-tools` and its version
disagrees with the stored preference, it redirects client-side to the
equivalent page in the preferred version
(`useActiveDocContext('versioned-tools').alternateDocVersions`, the same
per-doc "what's this page called in every other version" map
`DocVersionBanner` already relies on).

## Cutting Stable

`.github/workflows/cut-versions.yml` runs daily, fully automatically end
to end — not just the cut itself: it checks every submodule for a newer
tag (`scripts/auto-cut-versions.js`), and if any has one, that's the only
signal it waits for; it cuts Stable for every tool at once (the shared
instance only has one Stable version, covering every tool — there's no
way to cut just one tool's own portion of it), validates the result with
a full build and test run, and merges straight to `main` through a PR it
opens and merges itself. Nobody needs to remember to run this after a
release, and nobody needs to click merge either. There's no filtering on
tag name yet (e.g. skipping a pre-release/beta tag) — every tool currently
opted into versioning only ever tags real releases, so "newest tag"
already means "newest release" for all of them; a name-based filter is a
deliberate, not-yet-needed follow-up for the day that stops being true.

Cutting by hand (a brand new site's very first cut, before any tool has a
recorded tag to compare against; re-cutting a specific tool to a specific
non-newest tag; or just running it locally instead of waiting for the
schedule) is one command:

```bash
node scripts/cut-version.js stable [<toolId>=<tag> ...]
```

With no arguments, every tool with any tags gets cut at its own newest.
Pass `<toolId>=<tag>` pairs (ids from `scripts/versioned-tools.js`) to pin
specific tools instead — everything else still resolves to its own
newest. A tool whose submodule has no tags at all is left out of the cut
entirely; its Stable content just mirrors whatever's currently synced
from its own live `main`, same as Development, until it gets a first tag.

The script runs the whole procedure that used to be done by hand, for
every tool being cut, in order, and undoes every step's own side effects
even if a later step fails:

- Checks out each submodule being cut at its own target tag.
- Re-syncs every tool's docs together (`sync-external-docs.js`, with
  `SKIP_SUBMODULE_RESET` so the checkouts aren't immediately reverted).
- Clears any content and generated-sidebar cache left over from a
  *different* checkout before syncing, so a tag that predates a guide
  folder or a Doxyfile ends up genuinely sparse rather than inheriting
  another checkout's leftovers (`scripts/lib/prune.js`'s
  `pruneLegacyFolder`, plus wiping `scripts/generated/`).
- Prunes any `AUTO-GENERATED-*-TABLE` sub-page link that wouldn't
  actually exist in this cut (`pruneDanglingSubpageLinks`).
- Rewrites each tool's synced content's `tree/main/...` / `blob/main/...`
  GitHub links (READMEs, guides, the wrapper page's own "Source Code"
  button) to point at that tool's own tag instead (`rewriteMainLinksToTag`)
  — the file at `main` can already differ from what shipped in the tag
  Stable represents.
- Strips the "Use a released version" admonition that's real content on
  Development but wrong once frozen into Stable itself
  (`stripDevelopmentOnlyAdmonition`).
- Runs `docs:version:` into a scratch version name first, then renames it
  into place — `docusaurus.config.js`'s `lastVersion`/`versions` config
  has to keep resolving to an existing version for the entire duration of
  *any* `docusaurus` CLI invocation, including the cut itself, so
  deleting-then-recutting the real name directly trips
  `lastVersion: ... is invalid`.
- Restores every checked-out submodule's actual pinned commit and
  Development's own synced content, regardless of whether the cut itself
  succeeded.
- Records each cut tool's tag in `versioned-tools-stable.json` — read by
  `src/theme/DocVersionBanner` to name that tag on both versions, not
  hand-typed anywhere.
- Regenerates the versioned sidebar snapshot against the current live
  site nav tree (`regenerate-versioned-sidebars.mjs`), so this cut
  reflects the site's current navigation shape.

Review the resulting diff and run a full `npm run build` before
committing — the script prints this reminder itself. Unit tests for its
pure helpers live in `test/cut-version.test.js`.

## Checklist: adding versioning to a new tool

Assuming the tool already has its own wrapper page and a
`sync-external-docs.js` job under `versioned-tools/` (see
[Adding a new software tool](./adding-a-tool) — every tool lives there
from the start now, versioned or not, so nothing needs to move):

1. Add a `:::tip Use a released version` admonition to the tool's wrapper
   `index.mdx` — see any existing versioned tool's wrapper page for the
   exact text, and [API Stability Policy](/docs/api-stability). This page
   is what becomes Development's own content once the tool is versioned,
   so it needs the same "this documents unreleased `main`" nudge every
   other versioned tool's wrapper page already has. If the tool also gets
   a generated API reference (a `doxygen2docusaurus` job), nothing extra
   is needed there — `injectExperimentalNotice` in
   `sync-external-docs.js` already adds the matching notice to every page
   that pipeline produces, for any tool.
2. Register the tool in `scripts/versioned-tools.js` (submodule, repo URL,
   `toolPath`) — `scripts/cut-version.js` needs this entry to cut Stable
   for it.
3. In `scripts/site-nav-tree.mjs`'s `SITE_TREE`, replace the tool's
   `leaf(...)` entry with `versioned(label, '<plugin-id>')`.
4. In `sidebars.versioned-tools.js`, add this tool's own entry to the
   `activeItems` map — a simple `{type: 'doc', id: '<toolPath>/index',
   label: '<Tool>'}` for a one-page tool, or a nested category for a tool
   split into guides/API (see the existing `adaptive-grippers-cpp` entry
   there, and its `guidesCategory`/`doxygenApiCategory` helpers). For a
   split tool, guard *every* category whose `link` targets content that
   might not exist yet (an early tag can predate a guide folder or a
   Doxyfile) — check the real file exists on disk before including that
   category at all, the same way `guidesCategory`/`doxygenApiCategory`
   both do. Skipping this leaves a category whose `link` points at a doc
   id that doesn't exist in that version at all, which only Docusaurus's
   own build-time `checkSidebarsDocIds` catches — not the cut itself,
   which reports success.
5. If the tool also gets a generated API reference (a
   `doxygen2docusaurus` job in `external-jobs.js`), set
   `currentVersionPath: 'next'` on that job (must match
   `versions.current.path` exactly — see
   [Which version the root URL serves](#which-version-the-root-url-serves)).
   `routeBasePath` should already be `/docs/drivers` (the shared
   instance's own, set once for the tool's job regardless of whether it's
   versioned — see [One shared instance, not one per tool](#one-shared-instance-not-one-per-tool)).
6. If the tool already has a tag, cut Stable following
   [Cutting Stable](#cutting-stable) above. If it has no tags yet, skip
   this step entirely — the tool's content just tracks `main` on both
   versions until it does.
7. Run a full clean rebuild (`rm -rf .doxygen2docusaurus-staging build
   .docusaurus scripts/generated node_modules/.cache && npm run build`)
   and check: the tool's `<nav aria-label="Docs sidebar">` output contains
   the full site tree, not just its own branch, on every version; Stable
   (once cut) serves at the instance's own root URL and Development at
   `/next`; and, if the tool has a generated API reference, its
   cross-reference links resolve correctly under `/next`.
